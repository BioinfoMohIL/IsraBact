Typing Neisseria meningitidis on Terra

How to run the two typing workflows, how to read their results, and the rules the code applies to PubMLST answers.

Before you run

  • Store your PubMLST API key once, in the workspace

    In Terra, open Data, then Workspace Data, and add the variable pubmlst_api_key with your personal key (created at pubmlst.org/bigsdb). In the workflow configuration, set the input pubmlst_api_key to workspace.pubmlst_api_key. The script sends it to PubMLST in the X-API-Key header.

    A String input is written in clear in the task command and in the run metadata, so keep workspace access restricted and never paste the key in a WDL file, a script or a data table.

  • Launch one sample at a time

    Each typing query runs a BLAST search on the PubMLST server (up to 8 cores). Dr Jolley asked for sequential queries. Terra starts every selected row in parallel, so select a single row per submission and wait for it to finish before launching the next.

  • Read api_error as a technical problem

    If a column shows api_error, PubMLST could not be queried for it. Open nt_logs: it names the query that failed and the error type.

Run a workflow

Both workflows run the same typing: MLST, finetyping (PorA, FetA), BAST with MenDeVAR reactivity, and serogrouping. They differ only in what you start from.

wf_neisseria_typing_fasta Start from an assembly (FASTA)

What it runs

  1. Typing against PubMLST: MLST, finetyping, BAST and MenDeVAR.
  2. Serogrouping of the same assembly.

Reading the values

ValueMeaning
2 5-3Exact allele found in PubMLST.
0NadA only. Null allele: PubMLST found no nadA in this assembly, even with its low-stringency search. The gene is absent as far as can be told.
novelNadA only. A close match (at least 90% protein identity) that is not an exact allele: probably a new variant. The BAST is not assigned.
newSequence type only. The seven MLST alleles are exact, but PubMLST has no ST for that combination.
?PubMLST answered but found nothing usable for this value.
api_errorPubMLST could not be queried for this value (HTTP error, timeout, network). Open nt_logs for the error type, and rerun the sample.

The profile columns name every locus, so a row can be read at a glance:

mlst_profile abcZ:2,adk:3,aroE:4,fumC:3,gdh:8,pdhC:4,pgm:6
bast_profile fHbp_peptide:16,NHBA_peptide:20,NadA_peptide:0,PorA_VR1:5-3,PorA_VR2:10-4
finetyping_profile PorA_VR1:5-3,PorA_VR2:10-4,FetA_VR:F3-6

A missing locus is written adk:? or adk:api_error, never left out.

How the code decides

The typing code applies the rules below. They follow guidance from Dr Keith Jolley, curator of PubMLST, given by email on 23 to 25 November 2026. They are our reading of that guidance, not an official PubMLST statement.

NadA peptide

  1. Trust the BAST answer first.

    When PubMLST finds no nadA at all, even with its low-stringency search (50% identity over 30% of the alignment length), its BAST answer already contains NadA_peptide as 0. The code keeps that value and sends no further NadA query.

  2. If NadA is missing from that answer, query the NadA locus alone.
    • allele number exact match
    • novel closest match with at least 90% protein identity
    • 0 anything weaker, or nothing
  3. A novel NadA stops the BAST.

    bast_type and both MenDeVAR columns stay ?. The code never reports the closest BAST.

  4. If PubMLST cannot be reached, the value is api_error.

    A failed query is never turned into 0.

Why 90% protein identity

Dr Jolley's reasoning: PubMLST holds sequences for a very large number of NadA variants, so a new one is likely to differ by only one or two amino acids from its closest match. A real NadA should therefore score well above 90%.

DNA and protein identities cannot be compared directly. With four DNA bases, 25% identity is expected by chance. With 20 amino acids, 28% is a stronger signal, but still not convincing.

Example from one of our samples. The NadA locus query returned a best match of allele 113 with 27.96% identity (119 mismatches, 8 gaps). That is far below 90%, so NadA is 0. The BAST answer agreed: NadA 0, BAST 4928.

The 90% default comes from Dr Jolley's wording (“well over 90%”). It can be changed in the script with --nada-novel-min-identity.

BAST and MenDeVAR

Only an exact BAST is reported. The closest BAST is never reported: if a prediction of reactivity rests on one protein variant and the closest match differs exactly at that variant, the two would have completely different reactivities. MenDeVAR values come with the BAST.

fHbp, NHBA and the other loci

An allele without an exact match stays ?. The guidance above was given for NadA, so the code does not turn weak hits into novel or 0 for other loci.

New sequence types

new is written only when all seven MLST alleles are exact and PubMLST confirms it has no ST for that combination. If an allele is missing, the ST stays ?.

Being considerate to PubMLST

  • Every request carries your API key, so PubMLST knows who is querying.
  • Within a sample, queries run one after another. Network errors, server errors (5xx) and rate limiting (429) are retried up to three times, with growing pauses.
  • An authentication error (401 or 403) stops the remaining queries at once, and all values become api_error.
  • Other client errors (404, 451 and so on) are reported immediately, without retries.

Everything is traceable

  • nt_logs: the steps of the run, each failed query with its error type, and a summary of the columns marked api_error.
  • nt_api_raw_results: an archive of the raw PubMLST responses, including the body of error responses, named with the sample name.
  • nt_loci_best_matches: the closest match for loci without an exact allele.

Dr Jolley also noted that typing against locally downloaded databases is the more stable long-term option, since it does not depend on a remote service being available.
